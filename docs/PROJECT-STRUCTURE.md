## 2. What Each Major Folder Does

| Folder | Responsibility | Rule |
|---|---|---|
| `app/models/` | Describes tables as Python classes | No business logic |
| `app/services/` | All business rules, calculations, transactions, and external calls | The only place that changes stock, creates sales, sends email |
| `app/blueprints/` | One folder per feature. `routes.py` handles requests, `forms.py` validates input | Thin: read request, call a service, render or redirect |
| `app/templates/` | HTML pages, one folder per blueprint plus shared `base.html` and `partials/` | No business logic beyond display |
| `app/static/` | CSS, JavaScript, images | Each page-specific script lives in its own file |
| `app/utils/` | Small helpers (rupee format, IST dates) | Pure functions only |
| `migrations/` | Database version history | Generated, reviewed, never hand-edited casually |
| `tests/` | Automated tests | One test file per service or feature |
| `data/` | CSV templates and sample files | Fake data only |
| `docs/` | The project's memory | Updated at the end of every day |

## 4. Why This Structure

1. **Separation of concerns.** Routes, rules, and data live apart, so you can test rules without a browser and change the UI without breaking rules.
2. **One place for risky logic.** Stock changes only through `stock_service`, so the ledger cannot be bypassed by accident.
3. **Feature folders mirror screens.** When you work on Sales, everything is in `blueprints/sales/` and `templates/sales/`.
4. **Beginner-friendly.** Every file has one job and a predictable name.
5. **Deployment-friendly.** `wsgi.py` is the single entry point for local runs and for the host.
